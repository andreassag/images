# AGENTS.md — Development Guidelines for AI & Antigravity

This repository maintains optimized, multi-architecture Docker/OCI images for bioinformatics and structural biology tools. Follow these guidelines strictly when making modifications or adding new tools.

---

## 1. Repository Architecture & Layout

Each tool is located in a top-level directory containing exactly one generic `Dockerfile` and a `versions.txt` list of supported versions:

```
/
├── <tool>/
│   ├── Dockerfile          # Parameterized via ARG TOOL_VERSION
│   └── versions.txt        # Supported version strings, one per line (semver)
├── tests/
│   └── <tool>/
│       └── test.sh         # Test suite taking <image> and <expected_version>
├── .github/
│   ├── workflows/
│   │   └── build-container.yml   # Smart matrix CI/CD with BuildKit caching
│   └── dependabot.yml            # Auto-generated by scripts/generate-dependabot.sh
└── scripts/
    └── generate-dependabot.sh    # Scans top-level <tool>/Dockerfile entries
```

### Exceptions
- `pymol/` is a dedicated subfolder that contains additional runtime and GUI forwarding assets: `README.md`, `docker-compose.yml`, `docker-compose.linux.yml`, `docker-compose.mac.yml`, `pymolrc`, `pymolrc.py`, `license.lic.example`, and `examples/render_structure.py`.

## 2. Container Build Policies

### A. Avoid Pure Bioconda / Conda Installs
- For CLI tools (`clinker`, `cblaster`, `defense-finder`, etc.), **do not** use monolithic `mambaorg/micromamba:alpine` images that simply execute `micromamba install -c bioconda ...`.
- Instead, use multi-stage builds based on `python:3.12-slim` (or appropriate runtime).
- Build or fetch native binaries (HMMER, DIAMOND, skani, MMseqs2, etc.) from upstream releases or source in the builder stage.
- Install Python packages from official upstream source releases into a virtual environment (`/opt/venv`).
- Copy only the compiled binaries and `/opt/venv` into the final slim runtime image.
- **Exception**: PyMOL 3.x commercial GUI bundles distributed by Schrödinger use `mambaorg/micromamba:debian-slim` with system X11/Mesa/OpenGL libraries, because PyMOL requires heavy Qt/XCB graphics stacks and Schrödinger's proprietary packaging.

### B. Layer Caching & Build Arguments
- Place `ARG TOOL_VERSION` as late as possible in the Dockerfile (specifically right before downloading the tool source) so that expensive compilation stages (like HMMER or DIAMOND) remain cached across different versions of the Python package.
- In CI, BuildKit cache keys are scoped per tool: `type=gha,scope=${{ matrix.tool }}`.

### C. Non-Root Execution & Permissions
- Tools that require GUI display forwarding or persistent configuration (such as PyMOL) must run as a non-root user (e.g., user `pymol`, UID 1000, GID 1000) and support volume mounting of licenses or project directories.
- CLI batch tools default to standard slim container runtime conventions with `/data` work directory.

## 3. Version Management & CI/CD Workflow

### Adding a New Version to an Existing Tool
1. Append the new version string to `<tool>/versions.txt`.
2. Do not duplicate Dockerfiles. The CI change detection will automatically detect the added line in `versions.txt` via `git diff` and queue a build for only the added version.
3. If the new version becomes the highest version, CI will also tag it as `:latest`, `:minor`, and `:major`.

### Adding a New Tool
1. Create directory `<tool>/`.
2. Add `<tool>/Dockerfile` accepting `ARG TOOL_VERSION`.
3. Add `<tool>/versions.txt` listing supported versions.
4. Add test script `tests/<tool>/test.sh` taking arguments `$1` (image tag) and `$2` (expected version). Make sure it exits with code 0 on success.
5. Run `./scripts/generate-dependabot.sh` to update `.github/dependabot.yml`.
6. Update the tools table in `README.md`.

### Testing Verification
- Every test script under `tests/<tool>/test.sh` must verify:
  1. Exit code 0 on `--help` or headless execution.
  2. The version reported by the tool or environment matches `${EXPECTED_VERSION}`.
  3. Essential companion binaries or entrypoints are callable.
- Test scripts must be executable (`chmod +x tests/<tool>/test.sh`) and pass syntax checks (`bash -n tests/<tool>/test.sh`).

---

## 4. Dependabot Maintenance
- Never edit `.github/dependabot.yml` manually.
- Run `./scripts/generate-dependabot.sh` from the repository root whenever a tool is added or removed.
- Verify that every tool has exactly one entry pointing to `/<tool>`.
